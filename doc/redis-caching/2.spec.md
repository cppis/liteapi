## 구현 상세

### CacheService (`Services/CacheService.cs`)

**역할:** `IDistributedCache`를 래핑하여 모든 캐시 예외를 흡수한다.

**API:**
```
GetAsync<T>(key)    → 캐시 히트: T, 미스/실패: default
SetAsync<T>(key, value, ttl?)  → 저장 실패 시 무시
RemoveAsync(key)    → 삭제 실패 시 무시 (TTL 만료에 의존)
```

**메트릭 연동:**
- 모든 메서드에서 `TrackCacheOperationDuration`으로 소요 시간 측정 (get/set/remove 레이블)
- `GetAsync` 내부에서 키 prefix를 추출하여 (`"user:123"` → `"user"`) 히트/미스 기록
- 카디널리티 폭발 방지를 위해 전체 키가 아닌 prefix만 레이블로 사용

**DI 등록:** `Singleton` (IDistributedCache가 thread-safe)

### UserService (`Services/UserService.cs`)

**역할:** 엔드포인트와 데이터 계층 사이에서 캐시 로직을 캡슐화한다.

**Load 메서드 (로직 전):**

| 메서드 | 용도 | 캐시 사용 | ChangeTracker |
|--------|------|----------|---------------|
| `GetByIdAsync(userId)` | 읽기 전용 | 캐시 → DB 폴백 | `AsNoTracking` (추적 안 함) |
| `GetAllAsync()` | 목록 조회 | 캐시(30초) → DB 폴백 | `AsNoTracking` (추적 안 함) |
| `LoadAsync(userId)` | 쓰기용 | 사용 안 함 (DB 직접) | 추적됨 |

**Save 메서드 (로직 후):**

모든 쓰기 메서드는 명시적 트랜잭션을 사용하며, 캐시 무효화는 커밋 이후에 수행한다.

| 메서드 | 동작 | 트랜잭션 | 캐시 무효화 |
|--------|------|---------|------------|
| `SaveAsync(user)` | `BeginTransaction` → `SaveChangesAsync` → `Commit` → 캐시 삭제 | 명시적 | `user:{id}` 즉시 삭제 |
| `CreateAsync(user)` | `BeginTransaction` → `Add` + `SaveChangesAsync` → `Commit` | 명시적 | 없음 (목록은 TTL 만료) |
| `DeleteAsync(userId)` | `FindAsync` → `BeginTransaction` → `Remove` + `SaveChangesAsync` → `Commit` → 캐시 삭제 | 명시적 | `user:{id}` 즉시 삭제 |

**DI 등록:** `Scoped` (AppDbContext와 동일 생명주기)

### 트랜잭션 전략

**원칙: 캐시 무효화는 반드시 트랜잭션 커밋 이후에 수행한다.**

```
1. BeginTransaction
2. SaveChangesAsync (DB 변경)
3. CommitAsync (트랜잭션 확정)
4. Cache RemoveAsync (캐시 무효화)
```

이 순서의 이유:
- 커밋 전에 캐시를 삭제하면, 다른 요청이 DB에서 아직 커밋되지 않은 이전 데이터를 읽어 캐시에 넣을 수 있음
- 커밋 후 캐시 삭제가 실패하면, CacheService에서 예외를 흡수하고 TTL 만료에 의존

**장애 시나리오:**

| 시점 | 장애 | 결과 |
|------|------|------|
| SaveChangesAsync 실패 | DB 예외 | 트랜잭션 롤백, 캐시 변경 없음 |
| CommitAsync 실패 | DB 커밋 예외 | 트랜잭션 롤백, 캐시 변경 없음 |
| RemoveAsync 실패 | Redis 예외 | DB 커밋 완료, 캐시는 TTL 만료에 의존 |

### 엔드포인트 변경 (`Program.cs`)

모든 User CRUD 엔드포인트가 Load → Process → Save 3단계 패턴을 따른다:

| 엔드포인트 | Load | Process | Save |
|-----------|------|---------|------|
| `GET /api/users/{id}` | `GetByIdAsync` (캐시→DB, AsNoTracking) | — | — |
| `GET /api/users` | `GetAllAsync` (캐시→DB, AsNoTracking) | — | — |
| `POST /api/users` | — | — | `CreateAsync` (트랜잭션) |
| `PUT /api/users/{id}` | `LoadAsync` (DB직접, Tracked) | 프로퍼티 수정 | `SaveAsync` (트랜잭션) |
| `DELETE /api/users/{id}` | `DeleteAsync` (내부 처리, 트랜잭션) | — | — |
| `POST /api/users/{id}/add-gold` | `LoadAsync` (DB직접, Tracked) | Gold 증가 | `SaveAsync` (트랜잭션) |

**Lock 처리 변경:**
- 기존: `AcquireLockAsync(userId, dbContext)` / `ReleaseLockAsync(userId, dbContext)` 수동 관리
- 변경: `ExecuteWithLockAsync(userId, async () => { ... })` 사용
- 이유: 수동 Acquire/Release에 dbContext를 전달하지 않으면 내부에서 생성한 커넥션이 즉시 Dispose되어 lock이 해제됨

**Packet 엔드포인트:** `POST /api/packet/user`는 테스트 용도이므로 `AppDbContext` 직접 사용 유지. 목록 캐시는 TTL 만료로 처리됨.

### 헬스체크 (`Program.cs`)

- 기존: `app.MapGet("/health", ...)` 단순 lambda
- 변경: `app.MapHealthChecks("/health", ...)` ASP.NET Core Health Checks 미들웨어
- Redis 장애 시 `Degraded` 보고 (`Unhealthy`가 아님)
- 응답 형식: `{ status, checks: [{ name, status, description }], timestamp }`

### Prometheus 메트릭 (`Services/MetricsService.cs`)

추가된 메트릭:

| 메트릭 | 타입 | 레이블 | 설명 |
|--------|------|--------|------|
| `mini_server_cache_hits_total` | Counter | `key_prefix` | 캐시 히트 수 |
| `mini_server_cache_misses_total` | Counter | `key_prefix` | 캐시 미스 수 |
| `mini_server_cache_operation_duration_seconds` | Histogram | `operation` | 캐시 작업 소요 시간 (get/set/remove) |

CacheService의 모든 메서드에서 `TrackCacheOperationDuration`으로 소요 시간을 측정한다.

### Redis 설정 (`appsettings.yaml`)

```yaml
Redis:
  Connection: "localhost:6379"
  InstanceName: "liteapi:"
  DefaultTTLSeconds: 300    # 단일 엔티티 5분
  ListTTLSeconds: 30        # 목록 30초 (무효화 안 함)
```

| 캐시 키 | 데이터 | TTL | 무효화 |
|---------|--------|-----|--------|
| `liteapi:user:{userId}` | 단일 사용자 JSON | 300초 | 쓰기 시 즉시 삭제 (트랜잭션 커밋 후) |
| `liteapi:users:all` | 전체 사용자 목록 JSON | 30초 | 안 함 (TTL 만료에 의존) |

## 에러 처리

에러 처리는 **CacheService 한 곳에서만** 수행:

```
Endpoint → UserService → CacheService (try-catch) → IDistributedCache → Redis
                                         ↓ 실패 시
                                      return default / 무시
```

| 장애 상황 | 동작 | 서비스 영향 |
|----------|------|-----------|
| Redis 연결 실패 | 캐시 무시, DB 직접 조회 | **없음** |
| Redis 타임아웃 | 로그 경고, DB 폴백 | **없음** |
| Redis 서버 다운 | 모든 캐시 미스, DB 전량 처리 | **없음** (성능 저하만) |
| 서비스 기동 시 Redis 부재 | 정상 기동, 첫 접근 시 폴백 | **없음** |
