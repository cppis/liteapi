# Redis 캐싱 구현 리뷰

`1.plan.md` 계획 대비 `2.spec.md` 구현 결과를 분석한 리뷰 문서.

## 계획 대비 구현 준수 여부

| 항목 | 계획 | 구현 | 준수 |
|------|------|------|------|
| 핵심 원칙 (캐시 장애 ≠ 서비스 장애) | 모든 캐시 작업 try-catch | CacheService 3개 메서드 모두 try-catch | **준수** |
| Load → Process → Save 패턴 | 모든 엔드포인트 적용 | 6개 User 엔드포인트 모두 적용 | **준수** |
| 읽기/쓰기 Load 분리 | GetByIdAsync(캐시) / LoadAsync(DB) | 그대로 구현 | **준수** |
| 읽기 전용 AsNoTracking | 읽기 경로에서 ChangeTracker 비활성화 | GetByIdAsync, GetAllAsync에 AsNoTracking 적용 | **준수** |
| 목록 캐시 무효화 안 함 | TTL 30초만 의존 | SaveAsync/CreateAsync/DeleteAsync 모두 목록 무효화 없음 | **준수** |
| 단일 유저 캐시 즉시 무효화 | 쓰기 시 user:{id} 삭제 | SaveAsync, DeleteAsync에서 RemoveAsync 호출 | **준수** |
| Lock은 ExecuteWithLockAsync 사용 | 수동 Acquire/Release 금지 | Update, AddGold 모두 ExecuteWithLockAsync | **준수** |
| 에러 처리 CacheService 단일 계층 | UserService에서 캐시 예외 처리 안 함 | UserService에 try-catch 없음 | **준수** |
| 헬스체크 Degraded | Redis 장애 시 Unhealthy가 아닌 Degraded | `failureStatus: HealthStatus.Degraded` | **준수** |
| 메트릭 prefix 카디널리티 | key prefix만 레이블 사용 | `key[..key.IndexOf(':')]` 추출 | **준수** |
| 메트릭 소요시간 측정 | CacheOperationDuration Histogram | 모든 메서드에서 TrackCacheOperationDuration 호출 | **준수** |
| 트랜잭션 | 커밋 후 캐시 무효화 | 모든 Save 메서드에 명시적 트랜잭션 적용 | **준수** |

## 이전 리뷰 발견사항 반영 확인

| # | 발견사항 | 상태 |
|---|---------|------|
| 1 | `TrackCacheOperationDuration` 미호출 | **해결** — GetAsync/SetAsync/RemoveAsync 모두 호출 추가 |
| 2 | 읽기 전용 쿼리에 `AsNoTracking` 미적용 | **해결** — GetByIdAsync에 `AsNoTracking().FirstOrDefaultAsync()`, GetAllAsync에 `AsNoTracking().ToListAsync()` 적용 |
| 3 | 패키지 버전 계획 vs 실제 불일치 | **해결** — 1.plan.md 패키지 버전을 실제 설치 버전(10.0.5, 9.0.0)으로 업데이트 |

## 코드 품질

### CacheService — 문제 없음

- 모든 public 메서드에 try-catch + `TrackCacheOperationDuration` 적용
- 타이머가 try 블록 안에서 `using`으로 선언되어, 예외 시에도 duration이 기록됨
- prefix 추출 로직이 `GetAsync` 내부에서만 수행되어 일관성 있음

### UserService — 문제 없음

- 읽기 경로: `AsNoTracking` 적용으로 ChangeTracker 오버헤드 제거
- 쓰기 경로: 명시적 `BeginTransactionAsync` → `SaveChangesAsync` → `CommitAsync` 순서
- 캐시 무효화가 `CommitAsync` 이후에 위치하여, 커밋 전 stale 캐시 복원 문제 방지
- `await using var transaction`으로 예외 시 자동 Dispose(롤백)

### Program.cs — 문제 없음

- 서비스 등록 순서 적절
- 엔드포인트 주석에 Load/Process/Save 단계 표시
- Update/AddGold에서 `ExecuteWithLockAsync` 사용

### MetricsService — 문제 없음

- 캐시 메트릭 3종 모두 CacheService에서 호출 확인
- 미사용 코드 없음

### 트랜잭션 — 문제 없음

- `SaveAsync`: BeginTransaction → SaveChanges → Commit → Cache Remove 순서 정확
- `CreateAsync`: 동일 패턴 적용
- `DeleteAsync`: FindAsync(트랜잭션 밖) → BeginTransaction → Remove + SaveChanges → Commit → Cache Remove

## 결론

이전 리뷰의 3개 발견사항이 모두 반영되었고, 트랜잭션 기능이 계획/구현/문서에 일관되게 추가되었다.

구현 차단 요소 없음. 구현 완료 상태.
