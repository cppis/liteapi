# Redis 캐싱 도입 계획

EF Core DB 성능 개선을 위한 Redis 인메모리 캐싱 추가 계획

## 핵심 원칙

> **캐시 장애가 서비스 장애가 되어서는 안 된다.**
>
> Redis는 성능 최적화 수단이며, 핵심 의존성이 아니다.
> Redis 연결 실패, 타임아웃, 직렬화 오류 등 어떤 캐시 장애가 발생하더라도
> LiteApi는 DB 직접 조회로 정상 동작해야 한다.

이 원칙은 모든 구현 단계에 적용되며, 캐시 관련 코드는 반드시 다음을 준수한다:
- 모든 캐시 작업을 try-catch로 감싸고, 예외 시 로그만 남긴 뒤 DB로 폴백
- Redis를 optional dependency로 취급 (Redis 없이도 서비스 기동 가능)
- 헬스체크에서 Redis 상태는 `Degraded`로 보고 (서비스 전체를 `Unhealthy`로 만들지 않음)

## 1. 현재 상태 분석

### 데이터 접근 패턴
현재 모든 User CRUD 엔드포인트가 `AppDbContext`를 직접 사용하여 MySQL에 매번 쿼리를 실행한다.

| 엔드포인트 | 쿼리 패턴 | 캐싱 가치 |
|-----------|----------|----------|
| `GET /api/users` | `ToListAsync()` | 높음 - 전체 조회 빈도 높음 |
| `GET /api/users/{id}` | `FindAsync(id)` | 높음 - PK 조회, 캐시 적중률 높음 |
| `PUT /api/users/{id}` | `FindAsync` + `SaveChangesAsync` | 캐시 무효화 대상 |
| `DELETE /api/users/{id}` | `FindAsync` + `Remove` | 캐시 무효화 대상 |
| `POST /api/users/{id}/add-gold` | `FindAsync` + `SaveChangesAsync` | 캐시 무효화 대상 |
| `POST /api/users` | `Add` + `SaveChangesAsync` | 캐시 무효화 대상 |

### 문제점
- 읽기 요청마다 MySQL 네트워크 왕복 발생
- 동일 사용자를 반복 조회해도 매번 DB 쿼리 실행
- 전체 사용자 목록 조회 시 부하 증가 가능성

## 2. 목표

- 읽기 성능 향상: 자주 조회되는 데이터를 Redis에 캐싱
- DB 부하 감소: 불필요한 반복 쿼리 제거
- 데이터 정합성 유지: 쓰기 작업 시 캐시 무효화
- 기존 코드 최소 변경: 서비스 레이어 추가로 엔드포인트 로직 변경 최소화

## 3. 기술 선택

### 패키지
```xml
<PackageReference Include="Microsoft.Extensions.Caching.StackExchangeRedis" Version="10.0.5" />
<PackageReference Include="AspNetCore.HealthChecks.Redis" Version="9.0.0" />
```

### 선택 이유
- `Microsoft.Extensions.Caching.StackExchangeRedis`: `IDistributedCache` 구현체 제공, `StackExchange.Redis`를 내부 의존성으로 포함
- `AspNetCore.HealthChecks.Redis`: Redis 헬스체크 지원
- `IDistributedCache` 인터페이스: ASP.NET Core 내장 캐시 추상화 활용 가능

## 4. 캐싱 전략 — 모바일 게임서버 특성

### 트래픽 특성
- **읽기 >>> 쓰기**: 유저 정보 조회가 압도적 (로그인, 프로필, 랭킹 등)
- **단일 유저 조회가 핵심**: 트래픽 대부분이 `user:{id}`로 본인 데이터 조회
- **목록/랭킹은 드묾**: 실시간 정합성 불필요, 수 초 지연 허용

### 데이터 유형별 캐싱 정책

| 데이터 유형 | 캐시 키 | TTL | 무효화 | 이유 |
|-----------|---------|-----|--------|------|
| 단일 유저 | `user:{id}` | 300초 | 쓰기 시 즉시 삭제 | 재화/레벨 변경이 바로 반영되어야 함 |
| 목록/랭킹 | `users:all` | 30초 | **안 함** (TTL 만료에 의존) | 몇 초 stale 허용, 무효화 비용 불필요 |
| 조건부 쿼리 | — | — | — | 캐싱 안 함 (빈도 낮고 조합 다양) |

### 핵심 결정: 목록 캐시는 무효화하지 않는다

목록/랭킹 데이터는 쓰기 시 무효화하지 않고 짧은 TTL(30초)로 자연 만료시킨다.
- 게임서버에서 "랭킹이 30초 늦게 반영됨"은 문제가 아님
- 쓰기마다 목록 캐시를 삭제하는 비용이 사라짐
- 단일 유저 캐시만 즉시 무효화하므로 무효화 로직이 단순해짐

## 5. 구현 계획

### 아키텍처 개요 — Load → Process → Save 패턴

모든 API 엔드포인트는 3단계로 실행된다:

```
┌─────────────────────────────────────────────────────────┐
│                      Endpoint                           │
│                                                         │
│  1. Load    ─ UserService.LoadAsync / GetByIdAsync      │
│               (캐시/DB에서 필요한 데이터를 가져옴)        │
│                         ↓                               │
│  2. Process ─ 순수 인메모리 로직                          │
│               (DB/캐시 접근 없음, 비즈니스 로직만 실행)    │
│                         ↓                               │
│  3. Save    ─ UserService.SaveAsync                     │
│               (DB 저장 + 캐시 무효화를 한 번에 수행)      │
└─────────────────────────────────────────────────────────┘
```

```
┌──────────────┐    ┌──────────────┐    ┌──────────────┐    ┌─────────┐
│   Endpoint   │───>│  UserService │───>│ CacheService │───>│  Redis  │
│              │    │              │    │              │    │         │
│  1. Load     │    │  Load:       │    │  Get/Set/    │    └─────────┘
│  2. Process  │    │   캐시→DB    │    │  Remove      │
│  3. Save     │    │  Save:       │    │  (예외 흡수)  │
│              │    │   DB저장     │    └──────────────┘
│              │    │   →캐시무효화│
│              │    │              │    ┌─────────┐
│              │    │              │───>│  MySQL  │
└──────────────┘    └──────────────┘    └─────────┘
```

**설계 핵심:**
- **Load**: 읽기 전용은 캐시 → DB 폴백, 쓰기용은 DB 직접 조회(ChangeTracker 유지)
- **Process**: 엔드포인트에서 인메모리 객체만 조작. DB/캐시 접근 없음
- **Save**: DB 저장 + 해당 유저 캐시 무효화를 한 번에 수행
- 쓰기 경로에서 캐시를 거치지 않으므로 EF Core ChangeTracker 문제 없음
- **목록 캐시는 무효화하지 않음** — 짧은 TTL(30초)로 자연 만료

### Lock과의 관계

쓰기 작업에서 Lock은 Load → Process → Save 전체를 감싼다:

```
Lock Acquire
  └─ 1. Load    (DB에서 조회, ChangeTracker 추적)
  └─ 2. Process (인메모리 수정)
  └─ 3. Save    (DB 저장 + 캐시 무효화)
Lock Release
```

`DbLockService.ExecuteWithLockAsync`를 사용하면 내부에서 단일 scope/커넥션으로
lock을 유지하므로, 수동 Acquire/Release 시 커넥션이 닫혀 lock이 풀리는 문제를 방지한다.

### 5.1단계: Redis 연결 설정

**appsettings.yaml에 Redis 설정 추가:**
```yaml
Redis:
  Connection: "localhost:6379"
  InstanceName: "liteapi:"
  DefaultTTLSeconds: 300    # 단일 엔티티 캐시 만료 5분
  ListTTLSeconds: 30        # 목록 캐시 만료 30초 (무효화 안 함, TTL 만료에 의존)
```

**Program.cs에 서비스 등록:**
```csharp
// Redis 캐시 등록 — AddStackExchangeRedisCache는 서비스 등록만 수행하며
// 실제 Redis 연결은 첫 사용 시 lazy하게 이루어진다.
// 연결 실패 시에도 서비스는 정상 기동되며, CacheService 내부 try-catch로 폴백한다.
builder.Services.AddStackExchangeRedisCache(options =>
{
    options.Configuration = builder.Configuration["Redis:Connection"];
    options.InstanceName = builder.Configuration["Redis:InstanceName"];
});
```

### 5.2단계: CacheService 구현

**새 파일: `Services/CacheService.cs`**

```csharp
public class CacheService
{
    private readonly IDistributedCache _cache;
    private readonly MetricsService _metrics;
    private readonly ILogger<CacheService> _logger;
    private readonly TimeSpan _defaultTTL;

    public CacheService(
        IDistributedCache cache,
        MetricsService metrics,
        IConfiguration configuration,
        ILogger<CacheService> logger)
    {
        _cache = cache;
        _metrics = metrics;
        _logger = logger;
        _defaultTTL = TimeSpan.FromSeconds(
            configuration.GetValue<int>("Redis:DefaultTTLSeconds", 300));
    }

    public async Task<T?> GetAsync<T>(string key)
    {
        // 메트릭 레이블용 prefix 추출 ("user:123" → "user", "users:all" → "users")
        var prefix = key.Contains(':') ? key[..key.IndexOf(':')] : key;

        try
        {
            var cached = await _cache.GetStringAsync(key);
            if (cached is null)
            {
                _metrics.IncrementCacheMiss(prefix);
                return default;
            }
            _metrics.IncrementCacheHit(prefix);
            return JsonSerializer.Deserialize<T>(cached);
        }
        catch (Exception ex)
        {
            _logger.LogWarning(ex, "캐시 읽기 실패: {Key}. DB로 폴백", key);
            _metrics.IncrementCacheMiss(prefix);
            return default;
        }
    }

    public async Task SetAsync<T>(string key, T value, TimeSpan? ttl = null)
    {
        try
        {
            var json = JsonSerializer.Serialize(value);
            await _cache.SetStringAsync(key, json, new DistributedCacheEntryOptions
            {
                AbsoluteExpirationRelativeToNow = ttl ?? _defaultTTL
            });
        }
        catch (Exception ex)
        {
            _logger.LogWarning(ex, "캐시 쓰기 실패: {Key}. 무시하고 계속 진행", key);
        }
    }

    public async Task RemoveAsync(string key)
    {
        try
        {
            await _cache.RemoveAsync(key);
        }
        catch (Exception ex)
        {
            _logger.LogWarning(ex, "캐시 삭제 실패: {Key}. TTL 만료에 의존", key);
        }
    }
}
```

DI 등록: `builder.Services.AddSingleton<CacheService>();`

→ 검증: 단위 테스트로 Get/Set/Remove 동작 확인

### 5.3단계: UserService 구현

**새 파일: `Services/UserService.cs`**

캐시 로직을 서비스 레이어에 캡슐화한다. 엔드포인트는 `UserService`만 호출하며, 캐시 존재를 알지 못한다.

```csharp
public class UserService
{
    private readonly AppDbContext _db;
    private readonly CacheService _cache;

    private readonly TimeSpan _userTTL;
    private readonly TimeSpan _listTTL;

    public UserService(
        AppDbContext db,
        CacheService cache,
        IConfiguration configuration)
    {
        _db = db;
        _cache = cache;
        _userTTL = TimeSpan.FromSeconds(
            configuration.GetValue<int>("Redis:DefaultTTLSeconds", 300));
        _listTTL = TimeSpan.FromSeconds(
            configuration.GetValue<int>("Redis:ListTTLSeconds", 30));
    }

    // ── 캐시 키 ──
    private static string UserKey(ulong id) => $"user:{id}";
    private const string AllUsersKey = "users:all";

    // ══════════════════════════════════════════════════
    //  Load 메서드 — 엔드포인트 로직 전에 데이터를 가져옴
    // ══════════════════════════════════════════════════

    /// <summary>
    /// [읽기 전용 Load] 캐시 → DB 폴백.
    /// 반환된 엔티티는 ChangeTracker에 추적되지 않을 수 있음 (캐시 히트 시).
    /// 읽기 전용 엔드포인트에서만 사용.
    /// </summary>
    public async Task<User?> GetByIdAsync(ulong userId)
    {
        var cached = await _cache.GetAsync<User>(UserKey(userId));
        if (cached is not null)
            return cached;

        var user = await _db.Users.FindAsync(userId);
        if (user is not null)
            await _cache.SetAsync(UserKey(userId), user, _userTTL);

        return user;
    }

    /// <summary>
    /// [읽기 전용 Load] 목록 조회. 캐시 → DB 폴백.
    /// TTL 30초, 무효화 안 함.
    /// </summary>
    public async Task<List<User>> GetAllAsync()
    {
        var cached = await _cache.GetAsync<List<User>>(AllUsersKey);
        if (cached is not null)
            return cached;

        var users = await _db.Users.ToListAsync();
        await _cache.SetAsync(AllUsersKey, users, _listTTL);
        return users;
    }

    /// <summary>
    /// [쓰기용 Load] DB에서 직접 조회. ChangeTracker에 의해 추적됨.
    /// 호출자가 프로퍼티를 수정한 뒤 SaveAsync()를 호출하면 변경이 저장된다.
    /// 쓰기 엔드포인트에서만 사용.
    /// </summary>
    public async Task<User?> LoadAsync(ulong userId)
    {
        return await _db.Users.FindAsync(userId);
    }

    // ══════════════════════════════════════════════════
    //  Save 메서드 — 엔드포인트 로직 후에 변경사항을 저장
    // ══════════════════════════════════════════════════

    /// <summary>
    /// [Save] DB 저장 + 해당 유저 캐시 즉시 무효화.
    /// 목록 캐시는 무효화하지 않음 (TTL 만료에 의존).
    /// </summary>
    public async Task SaveAsync(User user)
    {
        user.UpdatedAt = DateTime.UtcNow;
        await _db.SaveChangesAsync();

        await _cache.RemoveAsync(UserKey(user.UserId));
    }

    /// <summary>
    /// [Save] 새 유저 생성 후 DB 저장.
    /// 목록 캐시는 무효화하지 않음 (TTL 만료에 의존).
    /// </summary>
    public async Task<User> CreateAsync(User user)
    {
        user.CreatedAt = DateTime.UtcNow;
        user.UpdatedAt = DateTime.UtcNow;

        _db.Users.Add(user);
        await _db.SaveChangesAsync();

        return user;
    }

    /// <summary>
    /// [Load + Save] 삭제는 Load와 Save가 결합된 단일 작업.
    /// DB에서 조회 → 삭제 → 캐시 무효화.
    /// </summary>
    public async Task<bool> DeleteAsync(ulong userId)
    {
        var user = await _db.Users.FindAsync(userId);
        if (user is null) return false;

        _db.Users.Remove(user);
        await _db.SaveChangesAsync();

        await _cache.RemoveAsync(UserKey(userId));
        return true;
    }
}
```

DI 등록: `builder.Services.AddScoped<UserService>();`
(AppDbContext가 Scoped이므로 UserService도 Scoped)

→ 검증: 읽기 메서드에서 캐시 히트/미스, 쓰기 메서드에서 캐시 무효화 확인

### 5.4단계: 엔드포인트에 Load → Process → Save 패턴 적용

기존 엔드포인트에서 `AppDbContext` 직접 사용을 `UserService`로 교체하고,
모든 엔드포인트가 3단계 패턴을 따르도록 한다.

**읽기 엔드포인트 — Load만 수행:**

```csharp
// Get user by ID
// Load: 캐시 → DB 폴백
app.MapGet("/api/users/{userId:long}", async (ulong userId, UserService userService) =>
{
    // 1. Load
    var user = await userService.GetByIdAsync(userId);

    // 2. Process (없음 — 읽기 전용)

    // 3. Save (없음 — 읽기 전용)
    return user is not null ? Results.Ok(user) : Results.NotFound();
});

// Get all users
// Load: 캐시(TTL 30초) → DB 폴백
app.MapGet("/api/users", async (UserService userService) =>
{
    // 1. Load
    var users = await userService.GetAllAsync();

    return Results.Ok(users);
});
```

**쓰기 엔드포인트 — Load → Process → Save:**

```csharp
// Create user
app.MapPost("/api/users", async (User user, UserService userService) =>
{
    // 1. Load (없음 — 새 엔티티)

    // 2. Process (없음 — 입력값 그대로 저장)

    // 3. Save
    var created = await userService.CreateAsync(user);
    return Results.Created($"/api/users/{created.UserId}", created);
});

// Update user (with lock)
app.MapPut("/api/users/{userId:long}", async (
    ulong userId,
    User updatedUser,
    UserService userService,
    DbLockService lockService) =>
{
    var result = await lockService.ExecuteWithLockAsync(userId, async () =>
    {
        // 1. Load — DB에서 직접 조회 (ChangeTracker 추적)
        var user = await userService.LoadAsync(userId);
        if (user is null)
            return Results.NotFound();

        // 2. Process — 인메모리 수정만 (DB/캐시 접근 없음)
        user.Username = updatedUser.Username;
        user.Email = updatedUser.Email;
        user.Level = updatedUser.Level;
        user.Experience = updatedUser.Experience;
        user.Gold = updatedUser.Gold;

        // 3. Save — DB 저장 + 캐시 무효화
        await userService.SaveAsync(user);
        return Results.Ok(user);
    });

    return result ?? Results.Conflict(new { error = "LOCK_FAILED",
        message = "Could not acquire lock for user update" });
});

// Delete user
app.MapDelete("/api/users/{userId:long}", async (ulong userId, UserService userService) =>
{
    var deleted = await userService.DeleteAsync(userId);
    return deleted ? Results.NoContent() : Results.NotFound();
});

// Add gold to user (with lock)
app.MapPost("/api/users/{userId:long}/add-gold", async (
    ulong userId,
    int amount,
    UserService userService,
    DbLockService lockService,
    ILogger<Program> logger) =>
{
    var result = await lockService.ExecuteWithLockAsync(userId, async () =>
    {
        // 1. Load — DB에서 직접 조회 (ChangeTracker 추적)
        var user = await userService.LoadAsync(userId);
        if (user is null)
            return Results.NotFound(new { error = "User not found" });

        // 2. Process — 인메모리 수정만
        user.Gold += amount;

        // 3. Save — DB 저장 + 캐시 무효화
        await userService.SaveAsync(user);

        logger.LogInformation("Added {Amount} gold to user {UserId}. New balance: {Gold}",
            amount, userId, user.Gold);
        return Results.Ok(new { userId, newGold = user.Gold, addedAmount = amount });
    });

    return result ?? Results.Conflict(new { error = "LOCK_FAILED" });
});
```

**패턴 요약:**

| 엔드포인트 | Load | Process | Save |
|-----------|------|---------|------|
| `GET /api/users/{id}` | `GetByIdAsync` (캐시→DB) | — | — |
| `GET /api/users` | `GetAllAsync` (캐시→DB) | — | — |
| `POST /api/users` | — | — | `CreateAsync` |
| `PUT /api/users/{id}` | `LoadAsync` (DB직접) | 프로퍼티 수정 | `SaveAsync` |

## 6. 캐시 키 설계

```
liteapi:user:{userId}     → 단일 사용자 JSON (TTL 300초, 쓰기 시 즉시 무효화)
liteapi:users:all          → 전체 사용자 목록 JSON (TTL 30초, 무효화 안 함)
```

- prefix `liteapi:`는 Redis InstanceName으로 자동 적용
- 단일 유저: TTL 300초 + 쓰기 시 즉시 삭제 → 정합성 보장
- 목록: TTL 30초, 무효화 없음 → 최대 30초 stale 허용, 무효화 비용 제거

## 8. 에러 처리 전략 (핵심 원칙 적용)

**캐시 장애 = 서비스 장애가 되어서는 안 된다.**

### 에러 처리 계층

에러 처리는 **CacheService 한 곳에서만** 수행한다.
UserService는 CacheService를 호출할 뿐, 캐시 관련 예외를 별도로 처리하지 않는다.

```
UserService → CacheService (try-catch, 예외 흡수) → IDistributedCache → Redis
                                                      ↓ 실패 시
                                                   return default / 무시
```

- `GetAsync`: 실패 시 `default` 반환 → UserService가 DB 조회
- `SetAsync`: 실패 시 무시 → 다음 요청에서 다시 시도
- `RemoveAsync`: 실패 시 무시 → TTL에 의해 자연 만료

### 장애 시나리오별 동작

| 장애 상황 | 동작 | 서비스 영향 |
|----------|------|-----------|
| Redis 연결 실패 | 캐시 무시, DB 직접 조회 | **없음** |
| Redis 타임아웃 | 로그 경고, DB 폴백 | **없음** |
| 캐시 직렬화 오류 | 해당 키 무시, DB 조회 | **없음** |
| Redis 서버 다운 | 모든 캐시 미스, DB 전량 처리 | **없음** (성능 저하만 발생) |
| Redis 데이터 유실 | 자연스러운 캐시 미스 | **없음** |

### 서비스 기동 시

`AddStackExchangeRedisCache`는 서비스 등록만 수행하며 실제 Redis 연결은 첫 사용 시 lazy하게 이루어진다. 따라서 Redis가 내려가 있어도 서비스는 정상 기동된다. 첫 캐시 접근 시 연결 실패가 발생하면 CacheService의 try-catch에서 흡수하고, DB 직접 조회로 동작한다.

### 헬스체크

Redis 장애 시 전체 헬스체크를 `Unhealthy`로 만들지 않는다:
```csharp
builder.Services.AddHealthChecks()
    .AddRedis(redisConnection, name: "redis",
        failureStatus: HealthStatus.Degraded);  // Unhealthy가 아닌 Degraded
```

## 11. 트랜잭션 전략

### 원칙: 캐시 무효화는 반드시 트랜잭션 커밋 이후에 수행한다

DB 저장과 캐시 무효화는 원자적으로 묶을 수 없다 (Redis와 MySQL은 별개 시스템).
따라서 다음 순서를 보장한다:

```
1. BeginTransaction
2. SaveChangesAsync (DB에 변경 반영)
3. CommitAsync (트랜잭션 확정)
4. Cache RemoveAsync (캐시 무효화)
```

이 순서가 중요한 이유:
- **커밋 전에 캐시를 삭제하면**: 다른 요청이 DB에서 아직 커밋되지 않은 이전 데이터를 읽어 캐시에 넣을 수 있음 (stale 캐시 복원)
- **커밋 후에 캐시 삭제가 실패하면**: TTL에 의해 자연 만료되므로 문제 없음 (핵심 원칙 적용)

### UserService 쓰기 메서드의 트랜잭션 적용

```csharp
public async Task SaveAsync(User user)
{
    user.UpdatedAt = DateTime.UtcNow;

    // 1. 트랜잭션 시작
    await using var transaction = await _db.Database.BeginTransactionAsync();
    // 2. DB 저장
    await _db.SaveChangesAsync();
    // 3. 트랜잭션 커밋
    await transaction.CommitAsync();

    // 4. 커밋 성공 후에만 캐시 무효화
    await _cache.RemoveAsync(UserKey(user.UserId));
}
```

### 장애 시나리오

| 시점 | 장애 | 결과 |
|------|------|------|
| SaveChangesAsync 실패 | DB 예외 | 트랜잭션 롤백 (Dispose), 캐시 변경 없음. 정상 |
| CommitAsync 실패 | DB 커밋 예외 | 트랜잭션 롤백, 캐시 변경 없음. 정상 |
| RemoveAsync 실패 | Redis 예외 | DB는 이미 커밋됨. CacheService에서 예외 흡수. TTL 만료에 의존. 정상 |

### 향후 다중 엔티티 트랜잭션

여러 엔티티를 하나의 트랜잭션으로 묶어야 하는 경우 (예: 골드 이체):

```csharp
public async Task TransferGoldAsync(ulong fromId, ulong toId, long amount)
{
    var from = await _db.Users.FindAsync(fromId);
    var to = await _db.Users.FindAsync(toId);

    from!.Gold -= amount;
    to!.Gold += amount;

    await using var transaction = await _db.Database.BeginTransactionAsync();
    await _db.SaveChangesAsync();
    await transaction.CommitAsync();

    // 커밋 후 양쪽 캐시 모두 무효화
    await _cache.RemoveAsync(UserKey(fromId));
    await _cache.RemoveAsync(UserKey(toId));
}
```

- **Redis Pub/Sub**: 다중 인스턴스 환경에서 캐시 무효화 전파 (장애 시 TTL 만료로 폴백)
- **Rate Limiting**: Redis 기반 API 호출 제한 (장애 시 제한 없이 통과로 폴백)
- **새로운 Entity 추가 시**: 동일 패턴으로 `ItemService`, `GuildService` 등 추가
